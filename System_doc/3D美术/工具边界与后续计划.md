# 3D 美术 · 工具边界与后续计划

**日期**：2026-09-09  
**锁定**：本站是网页（方案 B：Three.js），不是游戏工程。

Houdini、Unity **不是** Blender 建模之后的二次优化，也 **不负责** 走廊里的实时光影交互。第一期 / 第二期不要装、不要预埋半成品工程。

## 1. 当前交付链（已锁定）

```
Blender 形体 + UV
    → 拆 albedo / roughness / normal（源可 PNG）
    → 压 JPG + 不带贴图的瘦 GLB
    → 前端 MeshStandardMaterial 挂同一套 JPG，实例化门 / 灯
    → Three.js 实时打灯、阴影、开门 rotateY
```

操作步骤见 [材质交付操作.md](材质交付操作.md)。

| 环节 | 谁做 | 不是谁做 |
| --- | --- | --- |
| 门套、门扇、五金形体 | Blender | Houdini 精修、Unity 导入再做一遍 |
| 木纹 / 黄铜 PBR | Substance 或 Poly Haven → JPG | Houdini 材质网、Unity Shader Graph |
| 灯塘、门上高光、墙裙明暗 | 前端吊灯 + `MeshStandardMaterial` | Houdini 灯光、Unity Enlighten 烘焙 |
| 面数、铰链、包体 | TA 过 GLB | Unity 批处理 / Houdini 减面作为本期工序 |

运行时优化也在这条链上：三角上限、JPG 体积、8 扇门共用一份 GLB。不换引擎。

## 2. Houdini：程序化特效 / 模拟

Houdini 产出粒子、破碎、布料、烟雾体积，再烘焙成缓存给影视或游戏播。它 **不在浏览器里跑**，也不能替代 Three.js 打灯。

| 它擅长 | 和本站的关系 |
| --- | --- |
| 灯尘体积、雾柱、烟 | 现网用 `fog` + 吊灯更轻；Houdini 体积进网页过重 |
| 门炸开、墙碎、碎片刚体 | 第一期禁止物理；以后若做破坏镜头才考虑 |
| 几百扇程序化不同的门 | 8 扇门共用一份 `corridor_door.glb`，用不到 |
| 复杂程序化墙裙 / 地板 | Blender 凹板已经够 |

**触发条件（以后才开）：** 产品明确要做「走廊崩塌、烟尘灌入、碎玻璃」这类镜头，而不是把门模再优化一遍。

**那时的工序：** Houdini 模拟 → 烘焙 Alembic / 点缓存 / 序列帧 → 再评估能不能压进网页。缓存进 `public` 前须 TA 批体积。禁止把 `.hip` 工作文件当网页资源。

## 3. Unity：游戏客户端，不是本站渲染器

本仓库是 Vite + React + R3F。Unity（含 **Unity 5**）主场是可执行客户端或 Unity WebGL 包，接不进现有路由 / HUD / `rooms.json` 状态机。

### Unity 5（2015）

不要用。WebGL 过时，和当前站点叠在一起只会增大包体、拉长加载，也拿不到仍在维护的烘焙 / HDRP 工具链。

Unity 5 当时强的是 Enlighten 烘焙 GI、PBR 着色器——那是 **换引擎之后** 才吃得到的能力，不是给现有 GLB 加一层。

### 若以后改做独立 3D 应用（未开期）

相对现在的网页，新版本 Unity（应看 **Unity 6**，不要 Unity 5）或 Unreal 可能提供：

| 能力 | 说明 |
| --- | --- |
| 烘焙 GI / lightmap | 走廊灯塘预先烤进贴图，室内更匀、省运行时灯光 |
| 光照探针、遮挡剔除、LOD | 大场景才有意义 |
| 物理、导航、过场 | 与扩展模块里的 Rapier 是同一类需求，但是另一套工程 |

**触发条件：** 产品改成「可下载展馆 / 高品质预烘焙室内」，并接受 **重做一款客户端**，而不是给个人站插 Unity WebGL。

未触发前：继续 Three.js；重力碰撞若要做，走 [扩展模块](../产品/第二期/扩展模块_物理与后端.md) 的 Rapier，仍在网页里。
